# 问题理解分层方案设计（可实施版）

## 1. 背景与当前实现现状

当前项目的问题理解主逻辑集中在 `app/services/query_understanding.py`，对外仍然输出统一的 `QueryUnderstandingResult`，供 `chat.py -> retrieval_langchain.py -> qa_langchain.py` 继续使用。

现状上，一次问题理解调用会混合完成以下任务：

1. 路由判断（`kb_qa / out_of_scope`）
2. 追问检测（`is_follow_up`）
3. 上下文依赖判断（`need_context`）
4. 改写 query（`rewrite_query`）
5. 关键词抽取（`keywords_hit`）
6. 实体抽取（`entities`）
7. 检索扩展（`search_terms / search_queries`）

这个“一次调用做完分类和生成”的结构已经通过容错、兜底和规则覆写跑通，但仍有几个稳定性问题：

- 小模型更擅长分类，不擅长同时生成多路扩展字段。
- 分类任务要求收敛，扩展任务要求发散，混在一起会互相干扰。
- 当前追问改写质量很依赖规则层提供的 `previous_topic_query`、`rule rewrite_query` 和最近对话历史，不能在新方案里丢失。
- 当前检索分桶依赖 query 来源标签，若未来引入“两阶段扩展检索”，必须保留规则扩展和 LLM 扩展的来源差异。

因此，这份方案不追求推翻现有接口，而是在保留当前外部行为和降级链路的前提下，把内部实现拆成更稳的分层流程。

## 2. 设计目标

- 将“分类判断”和“检索扩展生成”拆成两段，降低单次模型调用复杂度。
- 保持 `QueryUnderstandingResult` 对外 schema 不变，避免影响现有问答、日志和前端展示。
- 规则层继续作为第一优先级兜底，任何模型失败都可以回到当前可用路径。
- 追问场景下保留当前实现的上下文锚点，不能因为分层而让短追问变差。
- 为“先行检索 + 后续扩展检索”预留可落地的数据结构，不只停留在概念上。
- 控制成本：不是所有 `kb_qa` 都进入大模型扩展，只在有收益的场景启用。

## 3. 总体思路

对外保留现有 `understand()` 和 `retrieve_with_understanding()` 的使用方式；对内拆成 3 层：

```text
用户问题
  │
  ▼
第 0 层：规则判断
  │
  ├─ 明显 out_of_scope -> 直接返回
  ├─ 明显 kb_qa 且无需扩展 -> 直接进入检索
  └─ 规则不确定 -> 第 1 层
              │
              ▼
第 1 层：小模型分类
  │
  ├─ out_of_scope -> 直接返回
  ├─ 低置信度 -> 回退规则结果
  └─ kb_qa -> 决定是否进入第 2 层
              │
              ▼
第 2 层：大模型扩展 + 先行检索并行
  │
  ├─ 先用规则改写/规则扩展启动首轮检索
  ├─ 大模型只补 rewrite/search_terms/search_queries
  └─ 追加检索后合并、重排、过滤、分桶
```

核心原则有两个：

1. `QueryUnderstandingResult` 仍然是后续链路唯一输入对象，分层是内部实现细节。
2. 第 2 层不是必走路径，而是“对当前检索有明显增益时才启用”的增强能力。

## 4. 与当前代码的对齐原则

### 4.1 对外 schema 不变

当前 `app/schemas.py` 已有 `QueryUnderstandingResult`，问答主链路、日志落库和前端展示都围绕它工作。新方案不直接替换它，而是：

- 新增内部分类结果对象 `QueryClassificationResult`
- 新增内部扩展结果对象 `QueryExpansionResult`
- 最终仍合成为 `QueryUnderstandingResult`

这样可以减少改动面，也能保持 `chat.py`、`qa_logging.py`、`QueryUnderstandingLog` 的兼容性。

### 4.2 追问锚点必须保留

当前追问改写质量依赖三类信息：

- `previous_topic_query`
- 规则层生成的 `rewrite_query`
- `history[-FOLLOW_UP_MAX_TURNS:]` 的最近对话

因此第 2 层绝不能只吃 `session_summary`。否则“这个能改吗”“那它支持离线吗”这类短追问会明显退化。

### 4.3 检索来源要保留阶段信息

当前 `retrieval_langchain.py` 已经按 query 来源做分桶挑选。如果未来加入“规则先检索，再用 LLM 扩展追加检索”，需要让检索结果知道自己来自哪一阶段，否则后面没法做：

- 分阶段配额控制
- 规则结果优先兜底
- 日志归因和效果评估

所以不能继续只用 `search_query / search_term` 两类粗标签。

### 4.4 SSE 进度协议需要前后端一起改

当前后端 `chat.py` 和前端 `ChatPage.vue` 都写死了 `start / understanding / retrieving / filtering / generating / completed`。如果要新增 `expanding`，必须：

- 后端进度事件增加新步骤
- 前端步骤映射同步增加新 key
- 兼容旧会话或旧步骤值

这属于真实改造范围，不能只算服务层内部调整。

## 5. 分层设计

### 5.1 第 0 层：规则判断

这一层沿用当前实现，不改判断逻辑，只明确它在新架构中的职责：

- `detect_keywords()`
- `detect_follow_up_by_rules()`
- `detect_route_by_rules()`
- `_heuristic_rewrite_query()` 产生规则侧追问改写锚点

输出建议拆成内部 `rule_result` 结构，至少包含：

```json
{
  "route": "kb_qa",
  "confidence": 0.96,
  "need_model": false,
  "is_follow_up": true,
  "need_context": true,
  "previous_topic_query": "物联网卡批量开户流程",
  "rule_rewrite_query": "物联网卡批量开户流程；补充追问：这个能改吗",
  "rule_search_terms": ["批量开户", "修改"],
  "rule_search_queries": ["批量开户 修改 主商品"]
}
```

注意：

- `previous_topic_query` 只作为内部锚点，不一定出现在最终对外 schema。
- `rule_rewrite_query` 不是最终结果，但它必须作为第 2 层输入和先行检索依据。

### 5.2 第 1 层：小模型分类

仅当规则层 `need_model=true` 时执行。

#### 输入

```json
{
  "current_query": "这个能改吗",
  "recent_history": [...],
  "session_summary": {...},
  "rule_signals": {
    "keyword_hits": {...},
    "follow_up": {...},
    "route_rules": {...}
  }
}
```

#### 输出

```json
{
  "route": "kb_qa | out_of_scope",
  "confidence": 0.85,
  "is_follow_up": true,
  "need_context": true
}
```

#### 实施要求

- 可以继续放在 `query_understanding.py` 内部实现，不要求先拆文件。
- 分类模型优先复用现有 `QUERY_UNDERSTANDING_PROVIDER / MODEL` 配置，后续再考虑独立配置。
- 低置信度时直接回退规则结果，保持当前 `SEMANTIC_CONFIDENCE_THRESHOLD` 逻辑。

### 5.3 第 2 层：大模型扩展

只有当最终路由为 `kb_qa`，且满足“值得扩展”的条件时才执行。

#### 推荐触发条件

第一版不要把所有 `kb_qa` 都送进大模型，而是优先复用当前思路，只在以下场景开启：

- `is_follow_up=true`
- 规则层认为需要语义补充（可复用当前 `_needs_model_enrichment()` 的条件）
- 规则检索词过短、过泛，预计召回质量不足
- 后续监控证明某些业务问法依赖扩展效果明显

不建议的第一版触发策略：

- 只要 `route=kb_qa` 就无脑进第 2 层
- 强关键词命中场景默认全量扩展

#### 第 2 层输入

这里必须按当前代码现状补齐追问锚点，建议输入如下：

```json
{
  "current_query": "这个能改吗",
  "classification": {
    "route": "kb_qa",
    "is_follow_up": true,
    "need_context": true
  },
  "recent_history": [...],
  "session_summary": {...},
  "previous_topic_query": "物联网卡批量开户流程",
  "rule_rewrite_query": "物联网卡批量开户流程；补充追问：这个能改吗",
  "business_keywords": [...],
  "rule_search_terms": ["批量开户", "修改"],
  "rule_search_queries": ["批量开户 修改 主商品"]
}
```

其中：

- `recent_history` 用于短追问补足上下文。
- `previous_topic_query` 是当前实现里最重要的追问主题锚点。
- `rule_rewrite_query` 用于约束大模型不要把改写做偏。

#### 第 2 层输出

```json
{
  "rewrite_query": "物联网卡批量开户流程 修改",
  "search_terms": ["批量开户", "修改", "主商品", "主产品"],
  "search_queries": ["批量开户 修改 主商品", "物联网卡 开户 修改流程"],
  "reason": "follow_up_to_kb_qa"
}
```

#### 输出约束

- `rewrite_query` 不得丢失规则层已确认的业务主体。
- `search_terms` 只输出短词，不输出整句。
- `search_queries` 建议 2-4 条，避免和原问题完全重复。
- 如果模型结果过弱，允许保留规则层字段，不强行覆盖。

## 6. 先行检索与追加检索

### 6.1 先行检索

在等待第 2 层返回时，先用规则层能稳定给出的 query 启动首轮检索：

- `raw_query`
- `rule_rewrite_query`
- `rule_search_terms`
- `rule_search_queries`

相比只用 `raw_query`，这样更符合当前追问链路的实际依赖，也能避免短追问首轮召回过弱。

### 6.2 追加检索

第 2 层返回后，再用以下字段做第二轮补充检索：

- `llm_rewrite_query`
- `llm_search_terms`
- `llm_search_queries`

### 6.3 来源标记调整

当前检索来源标签过粗。第一版建议改成以下更细的来源值：

- `raw_query`
- `rule_rewrite_query`
- `keyword`
- `entity`
- `rule_search_query`
- `rule_search_term`
- `llm_rewrite_query`
- `llm_search_query`
- `llm_search_term`

这样后续在 `retrieval_langchain.py` 里可以继续做分桶，但不会把规则扩展和 LLM 扩展混在一起。

### 6.4 分桶建议

第一版建议维持“主 query 优先、扩展 query 次之”的总体思想，只把 bucket 粒度细化：

```python
PRIMARY_SOURCE_QUOTAS = {
    "raw_query": 2,
    "rule_rewrite_query": 1,
    "llm_rewrite_query": 1,
}

EXPANSION_SOURCE_QUOTAS = {
    "rule_search_query": 1,
    "rule_search_term": 1,
    "llm_search_query": 2,
    "llm_search_term": 1,
}
```

这个配额不是最终常量，但数据结构应先支持这种区分。

## 7. 最终对象合成策略

对外仍然返回 `QueryUnderstandingResult`，合成原则如下：

- `route / confidence / is_follow_up / need_context` 来自“规则结果与分类结果合并后的最终分类结论”
- `rewrite_query` 优先使用稳定化后的第 2 层结果，其次是 `rule_rewrite_query`
- `search_terms / search_queries` 由规则结果和 LLM 结果合并去重
- `keywords_hit / entities / filters` 继续沿用当前逻辑
- `provider / model / fallback_used / reason` 如实记录实际走过的层级和是否降级

也就是说，分层不是新增一个全新返回结构，而是重新组织内部求值过程。

## 8. 代码改动范围

### 8.1 新增文件

- `app/services/query_expansion.py`
  - 第 2 层大模型扩展逻辑
  - 负责构造扩展 prompt、调用 provider、解析 JSON、做字段清洗

### 8.2 修改文件

| 文件 | 改动内容 |
|------|---------|
| `app/services/query_understanding.py` | 保留 `understand()` 对外接口，内部拆分规则判断、分类调用、最终合成 |
| `app/services/retrieval_langchain.py` | 支持先行检索、追加检索和更细粒度来源标签 |
| `app/services/chat.py` | `_prepare_turn_context()` 改成分层调用；流式进度增加 `expanding` |
| `app/schemas.py` | 新增 `QueryClassificationResult`、可选新增 `QueryExpansionResult` |
| `app/config.py` | 新增扩展层配置项和并行开关 |
| `knowledge_base_frontend/src/pages/ChatPage.vue` | 增加 `expanding` 流程节点和文案映射 |

### 8.3 大概率不需要改动的文件

- `app/services/minimax.py`
- `app/services/vector_store.py`
- `app/services/qa_langchain.py`
- `app/models.py`
- `app/routers/*`

注意：这里的“不需要改动”是指主逻辑不需要重写，不代表完全不会有导入或日志字段的小幅联动。

## 9. 配置项设计

在现有配置基础上新增：

```python
QUERY_EXPANSION_ENABLED = True
QUERY_EXPANSION_PROVIDER = "minimax"
QUERY_EXPANSION_MODEL = ""
QUERY_EXPANSION_MAX_OUTPUT_TOKENS = 1024
QUERY_EXPANSION_TIMEOUT_SECONDS = 15

PARALLEL_INITIAL_RETRIEVAL = True
QUERY_EXPANSION_FOR_FOLLOW_UP = True
QUERY_EXPANSION_FOR_RULE_ENRICHMENT = True
```

说明：

- 第一版可以让 `QUERY_EXPANSION_MODEL=""` 时回落到 `MINIMAX_MODEL_NAME`。
- 若后续需要更细控制，再拆分独立 provider/model 配置。

## 10. 实施步骤

建议按下面顺序推进，避免一次改太多导致链路难回归：

1. 在 `schemas.py` 增加内部分类/扩展 schema。
2. 在 `query_understanding.py` 里先把“规则判断结果”和“最终 `QueryUnderstandingResult`”拆开，但保持现有外部行为不变。
3. 新增 `query_expansion.py`，先实现同步版本，确保字段质量稳定。
4. 修改 `retrieval_langchain.py`，先支持新的来源标签和两阶段合并，不一定第一步就上并行。
5. 在 `chat.py` 接入第 2 层，并为流式进度增加 `expanding`。
6. 修改前端 `ChatPage.vue` 的流程步骤和文案映射。
7. 回归测试追问、超范围、FAQ、模型失败降级和流式显示。
8. 最后再把“同步扩展”升级为“并行扩展 + 先行检索”。

## 11. 验证重点

第一版至少要覆盖以下验证场景：

1. 明显超范围问题是否仍可直接返回，不触发第 2 层。
2. 强关键词 FAQ 是否不会无谓触发大模型扩展。
3. 短追问场景下，`rewrite_query` 是否保留了 `previous_topic_query` 的主体。
4. 第 2 层超时或解析失败时，是否仍能用规则首轮检索结果回答。
5. 检索日志里是否能区分 `rule_search_*` 和 `llm_search_*`。
6. SSE 流程里新增 `expanding` 后，前端是否正确展示，旧步骤是否兼容。

## 12. 风险与注意事项

- 并行检索和模型调用要避免复用同一个有状态数据库会话。
- 第 2 层输入不要只给 `session_summary`，否则追问质量会退化。
- 新来源标签上线后，分桶配额和评测报表要一起更新。
- 流式步骤新增 `expanding` 时，前端和后端必须同批上线。
- 第一版建议先做“结构拆分 + 数据结构补齐”，再做激进的并行优化。

## 13. 最终结论

这个分层方向是合理的，但在当前项目里要真正可实施，必须遵守 4 个落地前提：

1. 对外 `QueryUnderstandingResult` 不变。
2. 第 2 层显式继承 `previous_topic_query`、`rule_rewrite_query` 和最近对话。
3. 检索来源区分规则扩展和 LLM 扩展。
4. 把 SSE 和前端流程节点纳入正式改造范围。

按这个版本推进，分层方案就不再只是“模型拆两次调用”的概念描述，而是能直接指导当前代码实施的设计文档。
